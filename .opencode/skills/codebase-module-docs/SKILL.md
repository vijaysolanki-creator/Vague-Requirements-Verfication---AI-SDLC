# Codebase Module Docs

Read every file, then write one doc per module or feature. Not one doc per file.

## Output

```
<output>/
  README.md          index of everything
  architecture.md    system view and module map
  glossary.md        merged keywords
  _coverage.md       generated by the verify script
  modules/
    <module-or-feature>.md   one per module or feature
```

## Rules

1. Open and read every non-skipped file. Never document a file you have not read. Never invent behavior. If unclear, write `Unclear from code: <what>`.
2. No em dashes in any generated doc. Use commas, colons, or parentheses.
3. Keep docs simple and concise: bullets and tables, no filler. A module doc should be readable in a few minutes.
4. Every non-skipped file must appear in the `Files` table of exactly one module doc, with its path in backticks. The verify script enforces this.
5. Skipped files (lockfiles, binaries, build output, vendored code) are listed with a reason in `_coverage.md`, never silently dropped.
6. Write to disk as you go. Do not hold a module's notes only in memory.

## Workflow

Set `SKILL_DIR` to the directory containing this SKILL.md. Run scripts with their full path, since the working directory is the user's repo.

### Step 1: Scope

Confirm only what is missing: repo root (default: current directory), output folder (default `docs/codebase`; in Claude.ai use `/mnt/user-data/outputs/codebase-docs`), extra directories to exclude. Extract archives first.

### Step 2: Inventory and grouping

```bash
python $SKILL_DIR/scripts/inventory.py <repo_root> <output_folder>
```

This writes `_manifest.json` and `_progress.md` and prints files per module and layer. Each file has a `module` value. Review it and regroup by editing `module` in the manifest when needed:

- Split a module that mixes several features (for example a `backend` folder holding users, orders, and billing) into one unit per feature.
- Merge tiny modules into one.
- A feature that spans frontend and backend gets one doc covering both (use the Layer column in the Files table).
- Aim for roughly 3 to 25 files per doc.

Share the final module list and file counts with the user in two or three lines, then proceed. Order: shared and backend core, backend features, then frontend.

### Step 3: Document one module at a time

For each module, in batches of 10 to 15 files:

1. Read each file fully (chunk files over 800 lines).
2. Append its rows to `<output>/modules/<slug>.md` using `references/templates.md`. Slug is the module name with `/` replaced by `-`.
3. Tick the files in `_progress.md`.

After the last batch, complete the remaining sections of that module doc (Purpose, Features, Dependencies, Data flow, Keywords, Risks) from what you read. Finish and save one module before starting the next.

### Step 4: System docs

From the module docs only (do not re-read code):
- `architecture.md`: layers, module map, how frontend calls backend, main flows, external systems, Mermaid dependency diagram.
- `glossary.md`: merged, de-duplicated keywords, alphabetical, with the module doc where each lives.
- `README.md`: summary and links to everything.

### Step 5: Verify

```bash
python $SKILL_DIR/scripts/verify_coverage.py <output_folder>
```

Fix everything it reports (missing files in tables, missing sections, em dashes, missing system docs) and rerun until PASS.

## Context management

- Over about 150 source files: state the plan up front and finish plus verify one module before the next.
- If interrupted, resume from `_progress.md` and the verify output. Do not restart.
- Never paste whole files into docs. Reference by path and function or line range.

## Final response

Keep it short: output folder, number of module docs, files covered and skipped, anything marked `Unclear from code`, and 2 to 3 notable risks (dead code, missing auth, circular dependencies).
